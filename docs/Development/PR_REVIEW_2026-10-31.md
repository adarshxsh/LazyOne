## 2. Issues confirmed in code (`deployment` @ c683b3d)

These also appear in ARCHITECTURE_V2 §2. Items marked ➕ were found by this review only.

**Critical**
1. Browser reads and writes Firestore chat directly ([chat.html:67-115](../../basic/templates/chat.html#L67-L115)), the author id is supplied by the client, and there is no `firestore.rules` in the repo. Django permission checks are bypassed.
2. ➕ The `master` / `deployment` split described above.
3. `accept_cancellation` refunds the poster and reopens the task, so points are minted ([tasks.py:139-157](../../basic/views/tasks.py#L139-L157)). Fixed by #28 (unmerged).
4. `complete_task` takes no row lock, so the reward can be paid twice ([tasks.py:91-109](../../basic/views/tasks.py#L91-L109)).
5. State changes accept GET, so they are CSRF-able: take, complete, cancel, request/accept cancellation, abandon.
6. SQLite on Vercel's serverless filesystem means data is lost.
7. ➕ **CI workflow** `master:.github/workflows/claim-jules-pr.yml` runs on `pull_request_target` with `contents: write` and an optional PAT. It interpolates `${{ github.head_ref }}` straight into a shell `run:` step, which is a known script-injection pattern (branch names can contain shell metacharacters). It also force-pushes after re-authoring bot commits as a human. **Recommend deleting it**, or at minimum passing `head_ref` through an `env:` variable, dropping the PAT, and restricting it to same-repo PRs.

**High**
8. `withdraw_dispute` has no OPEN check, so a resolved dispute can be withdrawn and paid out again ([dispute.py:30-50](../../basic/views/dispute.py#L30-L50)).
9. ➕ `DisputeService.can_view` and `ChatService.can_read` let **any** logged-in user read every dispute and disputed chat ([permissions.py:8-13, 78-79](../../basic/services/permissions.py#L8-L13)). This is a privacy leak; access should be limited to parties, jurors and staff.
10. ➕ `resolve_dispute` checks the status before the transaction starts, with no lock (time-of-check vs time-of-use). Line 47 is dead code.
11. ➕ `add_task` checks the balance outside a locked transaction, and there is no `CHECK (rewards >= 0)`, so concurrent posts can overdraw.
12. `raise_dispute` overwrites old disputes in place, so history is lost.
13. `start_chat` uses the wrong URL kwarg, so it fails every time.
14. ➕ `send_message` swallows all exceptions (`except Exception: pass`).
15. Hardcoded fallback `SECRET_KEY`; duplicated settings blocks; Firebase initialised twice.
16. `Dispute.save()` triggers a blocking Firestore call with no reconciliation.

**Medium:** dead `FriendsRouter`, routing, consumers; unused `channels`/`daphne`; 3 tests; no CI test job; 6-line CONTRIBUTING.

## 3. Patterns and the architectural fix for each

| Pattern seen across PRs and code | v2 answer |
|---|---|
| Every flow repeats "F() update + ledger row + status change" by hand | Double-entry `ledger.transfer()` with escrow accounts and DB constraints (§4.1) |
| ~40 PRs re-add "status guards" | Single transition table with row lock and audit `TaskEvent` (§4.2) |
| Django and Firestore both written, from both client and server | Postgres authoritative; Firestore server-written, read-only to clients (§4.4) |
| Permission checks half-centralised; redirect vs 403 inconsistent | One policy layer used by web, API and Firestore member lists |
| Bots keep re-designing disputes | One written spec (§4.5) → small issues with acceptance tests |

## 5. Redesign checklist

**Must fix:** every Critical and High item in §2.

## 6. Bot workflow going forward

Unscoped bot runs produced ~300 PRs of duplicated work. Suggested process:
1. One GitHub issue per change, each linking the relevant ARCHITECTURE_V2 section, with explicit acceptance tests.
2. Bots target the trunk branch only, with one PR per issue. Close any PR that adds a conflicting migration number.
3. A human approves before merge, and CI must be green.
